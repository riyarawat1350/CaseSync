
AICTE CaseSync: Integrated Institution Complaint Monitoring & Coordination Dashboard
Smart India Hackathon 2026 | Problem Statement ID: 26264 | Organization: AICTE | Department: Regulation Bureau | Theme: Smart Automation | Category: Software
1. Executive Summary
AICTE receives complaints about technical institutions through several channels, and different Bureaus/Cells (Regulation Bureau, PGRC, regional offices and others) process them separately. Nobody has one real-time view of "which Bureau is doing what about Institution X". The result is duplicate effort, parallel or conflicting actions, delays and weak accountability.
CaseSync is a single-window web platform that (1) builds one master profile per institution, (2) pulls every complaint/case from every Bureau/Cell into one tracker, (3) automatically detects when different Bureaus are handling the same institution, even when complaint text and case numbers differ, (4) shows a live dashboard with SLA alerts, and (5) produces region-, bureau-, institution- and status-wise reports.
The key innovation is a hybrid Overlap Detection Engine: entity resolution (to identify the same institution) + rule logic (same category, open status, time window) + multilingual semantic similarity (to detect same-issue complaints). It raises the alert "Potential Overlapping Cases – Coordination Required" and opens a coordination thread between the officers concerned.

2.2 Root causes
No master institution identity. The same college may be recorded as "ABC Institute of Technology", "A.B.C. Inst. of Tech." or by an old/new Permanent ID.
Heterogeneous intake. Complaints arrive via PGRC portal, CPGRAMS-type grievance channels, email, letters, regional offices.
No common case taxonomy. Categories and statuses differ between Bureaus.
No cross-Bureau visibility, so overlap is discovered only by chance.
2.3 Constraints and assumptions
Users are government officials, so the UI must be simple, bilingual (English/Hindi) and role-restricted.
Source systems may not have clean APIs, so we need multiple ingestion modes (API, database sync, CSV/Excel upload, manual entry form).
Complaint data is sensitive (complainant identity, allegations), so strong security and privacy controls are needed.
The real dataset is not provided, so the prototype uses synthetic data with deliberately injected duplicates and name variations.

4. Proposed Solution: CaseSync
4.1 High-level architecture
The system has six layers:
Data Ingestion Layer. Connectors for the PGRC portal, RB case system, email/letter entry and Excel/CSV bulk upload. A scheduler runs near-real-time syncs (for example every 5 minutes) and API webhooks push instant updates.
Data Quality and Master Data Layer. Cleans and standardizes text, resolves institution identity against the AICTE Institution Master, and assigns every case a Unified Case ID.
Intelligence Layer. Overlap Detection Engine, category classifier, priority scorer and SLA engine.
Core Services Layer. Case service, workflow service, notification service, report service, search service, audit service.
Presentation Layer. Role-based web dashboard (responsive, bilingual) plus optional mobile view.
Security and Infrastructure Layer. Authentication (SSO/OTP), RBAC, encryption, audit logs, backups, deployment on MeitY-empanelled cloud or NIC.

5. Module-wise Design (mapped to the 8 expected features)
5.1 Centralized Institution Profile (Feature 1)
Institution Master with AICTE Permanent ID, name, aliases, address, district, state, region, institution type, approval status, contact details and head of institution.
Alias table stores earlier names, spelling variants and abbreviations to improve matching.
Consolidated history: timeline of all complaints and regulatory actions linked to the institution, with a risk indicator (for example number of open cases, repeated complaints, cases beyond SLA).
Institution 360 view: one page showing profile, open cases per Bureau, overlap alerts and past actions.
5.2 Complaint/Case Tracking (Feature 2)
Each case carries:
Unified Case ID (for example CS-2026-RB-000123) plus the source reference number from the originating system
Date of receipt, source channel, complainant type (student/faculty/other/anonymous)
Category and sub-category, short summary, full description, attachments
Current status, presently assigned Bureau/Cell and officer
Last action taken, next action required, date of last action, expected disposal date
Priority, SLA due date, link to related cases
Standard status model: Received → Under Scrutiny → Under Process → Action Initiated → Pending (Awaiting Input) → Transferred → Escalated → Disposed (with outcome code). Every Bureau's native status is mapped to this standard set so that reports are comparable.
5.3 Cross-Bureau/Cell Overlap Detection (Feature 3, the core innovation)
See Section 6 for the full design. Outputs: overlap alert, similarity explanation ("why flagged"), linking/mapping, lead-Bureau designation.
5.4 Real-Time Dashboard (Feature 4)
KPI cards: total received, pending, under process, disposed, transferred, escalated, beyond-timeline.
Charts: status distribution, Bureau-wise workload (stacked bars), region-wise heat map of India, monthly received vs. disposed trend, ageing buckets (0-7, 8-15, 16-30, 31-60, 60+ days).
Widgets: top institutions by open cases, overlap alerts needing coordination, SLA breaches today.
Drill-down: clicking any chart segment opens the filtered case list.
Live refresh via WebSocket or short-interval polling.
5.5 Workflow and Action History (Feature 5)
Append-only case timeline: every action stores who, which Bureau, timestamp, action type, remarks and attachments.
Transfer/escalation records capture from-Bureau, to-Bureau, reason, and acceptance by the receiving officer. Escalation follows a configurable hierarchy (Officer → Section head → Director/Advisor → Competent Authority).
Records are tamper-evident: updates create new entries, never overwrite old ones. A hash chain on audit entries can be added for integrity proof.
5.6 Search and Filters (Feature 6)
Search by Institution name (fuzzy and alias aware, so "ABC inst tech" still finds the college), AICTE Permanent ID, Case ID, Bureau/Cell, Region, category, status and date range. Filters can be combined and saved as named views. Results export to Excel/PDF.

6. Overlap Detection Engine (Innovation Detail)
The goal is to flag cases that concern the same institution (and possibly the same issue) across different Bureaus, even when IDs, names and text differ.
6.1 Step 1: Institution Entity Resolution
Matching is done in tiers, from most to least certain:
Exact match on AICTE Permanent ID (confidence 1.0).
Deterministic secondary keys: registered email domain, phone number, AISHE code, approval-file number.
Fuzzy name match on normalized names. Normalization lowercases text, removes punctuation, expands abbreviations (Inst. → Institute, Engg → Engineering, Tech → Technology) and removes stop words. Scored with Jaro-Winkler, token-set ratio and trigram similarity.
Address support: district, pincode and state agreement boost the score.
Human-in-the-loop: matches in the uncertain band (for example 0.70 to 0.90) go to a data steward for confirmation, and each confirmation is stored as a new alias so the system learns.
Indicative score: Institution_Match = 0.5·NameSim + 0.2·AddressSim + 0.2·IDOrContactMatch + 0.1·DistrictPinMatch

Output levels:

Medium (0.50 to 0.75): "Related Cases – Review" with an amber badge.
Institution-level notice: even when issues differ, the dashboard shows "Multiple Bureaus active on this institution" so no one acts blind.
6.3 Step 3: Explainability
Every alert shows why it fired: matched institution (with confidence), matched category, similar phrases highlighted, dates, and the Bureaus involved. This is important for official trust and for audit.
6.4 Step 4: Coordination Workflow
Alert appears for both Bureaus' officers.
Officer chooses: Link as related, Mark as duplicate (merge), Not an overlap (this feedback improves the model), or Request coordination.
A coordination thread opens with comments and attachments; either Bureau can propose a Lead Bureau.
The decision (for example, "RB will lead; PGRC to close with reference to RB action") is recorded with timestamp and approver.
Linked cases show a banner on each other so both sides stay aligned until disposal.
6.5 Worked example (from the problem statement)
Case P-101: Institution A, received by PGRC, "Under Process", category: faculty salary non-payment.
Case R-455: Institution A (spelled "A.B.C Inst of Engg & Tech" in RB records), received by RB, "Action Initiated", category: compliance deficiency, with salary-related remarks.
Engine resolves both to the same Permanent ID, finds different Bureaus, both open, related categories and high semantic similarity, giving a score of about 0.82.
Result: "Potential Overlapping Cases – Coordination Required" is shown to both officers and their supervisors.
6.6 Model approach and phasing
Phase 1 (prototype): rule-based plus fuzzy matching plus TF-IDF similarity. This is fully explainable and needs no heavy training.
Phase 2: multilingual embeddings with pgvector for semantic similarity, and a lightweight classifier (logistic regression or gradient boosting) trained on officer feedback to tune weights.
Phase 3: optional LLM-assisted summarization of related cases and suggested coordination notes, with human approval always required (the AI never takes decisions).

8. Security, Privacy and Compliance
Authentication: SSO with OTP/2FA; session timeout; device and IP logging.
Authorization: role-based plus Bureau-scoped and region-scoped access control. Sensitive fields (complainant identity, whistleblower complaints) masked by default.
Data protection: TLS in transit, AES-256 at rest, field-level encryption for personal data, regular encrypted backups.
Audit: every view, edit, export and login is logged. Audit logs are immutable.
Regulatory alignment: Digital Personal Data Protection Act 2023 principles (purpose limitation, minimal data, retention rules), GIGW guidelines for accessibility and government web standards, CERT-In security guidelines, and hosting on MeitY-empanelled cloud/NIC.
Safety: input validation, protection against OWASP Top 10 issues, file scanning for uploads, rate limiting.
Human accountability: AI only suggests; all decisions on linking, merging and disposal are taken by authorized officials.

14. Why This Solution Stands Out (USPs for judges)
Explainable hybrid AI, not a black box: every overlap alert shows reasons and a confidence score.
Handles real-world messiness: name variants, abbreviations, Hindi/English text, different case numbers.
Closes the loop: it does not stop at detection; it provides linking, coordination threads, lead-Bureau decisions and tracking until disposal.
Configurable, not hard-coded: SLA rules, statuses, categories, thresholds and Bureau mappings are admin-controlled.
Privacy-aware design: summary-level cross-Bureau visibility, masking, audit and DPDP alignment.
Scalable and extensible: adding a new Bureau or data source needs configuration, not redevelopment.
Human in control: AI suggests, officials decide.

17. Conclusion
CaseSync gives AICTE one source of truth for institution-related complaints. By combining a master institution identity, unified case tracking, explainable overlap detection, SLA-driven alerts and rich analytics, it removes duplicated effort, prevents conflicting parallel actions, and gives management real-time visibility. The design is practical for a hackathon prototype and scalable into a production-grade AICTE platform.
